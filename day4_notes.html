2. The 5 Major Attack Vectors & Production Defenses

2.1. ☠️ Attack #1: Data Tamper Attack (Amount ₹500 ➔ ₹5,000)

🎯 Hacker ka Plan:
Hacker Bluetooth hawa se packet capture karta hai aur payment amount ko ₹500 se badal kar ₹5,000 karne ki koshish karta hai, ya receiver ID badal kar apna account daalne ki koshish karta hai.

🧪 Chaos Simulator Code (`BridgeController.java` Line 59-73):

@PostMapping("/attack/tamper")
public ResponseEntity> attackTamper() {
    MeshPacket packet = MeshPacket.builder()
            .packetId("TAMPER-ATTACK-" + System.currentTimeMillis())
            .ttl(5)
            .createdAt(System.currentTimeMillis())
            .payload(new EncryptedPayloadDto("attacker-key", "attacker-iv", "altered-tampered-content"))
            .build();

    TransactionLedger result = ingestionService.ingest(packet);
    return ResponseEntity.ok(Map.of(
            "status", result.getStatus().name(), // ➔ "TAMPERED"
            "message", "Stage-2 Checksum Mismatch: Altered ciphertext detected and rejected as TAMPERED"
    ));
}

🛡️ Hamara Dual-Layer Defense:

  • Tier-1 (Ingestion Gateway - Stage 2): Gateway check karta hai: SHA-256("altered-tampered-content") == packetId? Hash mismatch hote hi packet **2 millisecond me reject** ho jata hai as TAMPERED.
  • Tier-2 (Settlement Engine): Agar hacker bahar ka barcode bhi naya bana le, toh jab Bank AES-GCM tijori kholega, 128-bit GMAC Authentication Tag fail ho jayega aur Java turant AEADBadTagException throw kar dega!

2.2. 🔁 Attack #2: The Replay Attack (Duplicate Payment Fraud)

🎯 Hacker ka Plan:
Hacker ciphertext badalta nahi hai. Wo wahi valid ₹500 wala packet capture karke server par 10 baar spam karta hai taaki Sundram ke account se 10 baar paise cut jayein!

🧪 Chaos Simulator Code (`BridgeController.java` Line 76-97):

@PostMapping("/attack/replay")
public ResponseEntity> attackReplay() {
    String sampleCiphertext = "replay-attack-sample-data";
    String packetId = computeSha256(sampleCiphertext);

    // Pehle hi Redis me claim kar diya taaki packet duplicate ban jaye!
    idempotencyService.claim(packetId);

    MeshPacket packet = MeshPacket.builder().packetId(packetId)...build();
    TransactionLedger result = ingestionService.ingest(packet);
    return ResponseEntity.ok(Map.of(
            "status", result.getStatus().name(), // ➔ "DUPLICATE"
            "message", "Stage-3 Redis Lock: Duplicate packet blocked by Redis SETNX"
    ));
}

🛡️ Hamara Defense:

  • Stage-3 Redis SETNX Lock (25h TTL): Pehle packet par key set hui `zeromesh:packet:` = `PROCESSING`. Jab duplicate packet 0.1ms baad aaya, Redis ne `SETNX` par **`false` (0)** return kiya. Gateway ne use Kafka ke aane se pehle hi drop kar diya!
  • PostgreSQL Tier-2 Defense: Agar Kafka lag se consumer tak message dobara gaya, toh database ke packet_id UNIQUE constraint par duplicate pakda jayega. Extra transfer: **₹0.00**!

2.4. 🌪️ Attack #4: Sybil & Broadcast Storm Denial-of-Service (DoS)

🎯 Hacker ka Plan:
Hacker metro ke andar ek rogue device chalata hai jo 1 second me 1,00,000 nakli packets Bluetooth par blast karta hai taaki sabhi phones ki battery drain ho jaye aur network crash ho jaye!

🛡️ Hamara Defense:

  • TTL = 5 Hop Decay: Har jump par TTL minus hota hai (5 ➔ 4 ➔ 3 ➔ 2 ➔ 1 ➔ 0). Jaise hi `TTL == 0`, phone forwarding rok deta hai. Koi packet infinite loop me nahi ghoom sakta!
  • Fast-Fail Ingestion Gateway: Gateway Stage 1 aur Stage 2 par in-memory RAM me 2ms ke andar nakli packets ko drop kar deta hai. Heavy Kafka aur Postgres tables tak garbage pahunchta hi nahi hai!

2.5. 🏃 Attack #5: Multi-Bridge Concurrent Flush Race Condition (Dave vs Bob)

🎯 The Subway Exit Race:
Sundram ka ek hi payment packet metro mesh me Bob aur Dave dono ke phones par relay hua tha. Dono alag-alag escalators se nikal kar theek usi millisecond me POST /api/v1/mesh/flush call karte hain!

🛡️ Hamara Defense:

  • Dono Gateway instances ek hi **Shared Redis Cluster** se judte hain.
  • Redis ka **`SETNX` atomic single-threaded operation** hai:
    • Dave ki request 1 nanosecond pehle pahunchi: Redis returns `1` (True) ➔ Proceed to settle.
    • Bob ki request 1 nanosecond baad aayi: Redis returns `0` (False) ➔ Drop as DUPLICATE!
  • Single payment hi process hoti hai, zero double-debiting!

3. Deep Architectural Clarifications (Sundram's Killer Doubts)

3.1. Kya Settlement Service Redis me Deduplication Check karti hai?

⚠️ The Absolute Architectural Truth:
NAHI! Settlement Consumer Redis me Deduplication Check NAHI lagata!
• Deduplication ka poora kaam: Ingestion Gateway + Redis SETNX (claim) sambhalta hai.
• Settlement Service ka kaam: Settlement Service duplicate rokne ke liye PostgreSQL Database use karti hai (transaction_ledger table ka packet_id UNIQUE constraint).
• Settlement Redis me sirf Status Update karti hai:
  • Payment success hone par: idempotencyService.markSettled(packetId) (Status ko "PROCESSING" se "SETTLED" karti hai).
  • Payment fail hone par: idempotencyService.release(packetId) (Lock release karti hai).

3.2. Redis Lock Key ka Format kya hota hai?

Hamare code (`IdempotencyService.java`) me key exact packetId ke base par banti hai:

VALUE: "PROCESSING" (later updated to "SETTLED")
TTL:   25 Hours (90,000 Seconds = 24h window + 1h safety buffer)

3.4. `TTL = 5` Hop Concept Deep-Dive

  • Hop kya hai? Ek phone se doosre phone par Bluetooth se packet ka jump karna = 1 Hop.
  • TTL kya hai? TTL koi second ya minute nahi hai. Ye ek Hop Countdown Counter hai!
  • Countdown: Sundram (TTL=5) ➔ Bob (TTL=4) ➔ Charlie (TTL=3) ➔ Dave (TTL=2) ➔ P5 (TTL=1) ➔ P6 (TTL=0 🛑 STOP).
  • Kyu zaroori hai? Agar limit na ho, toh packet metro ke 500 phones ke beech gol-gol ghoomta rahega (Broadcast Storm), saare phones ubalne lagenge aur battery 0% ho jayegi!
  • 5 Hops hi kyu? Bluetooth range $\approx 10\text{m}$. $5 \text{ hops} \times 10\text{m} = \mathbf{50\text{ Meters}}$. Ek metro coach ya platform 40-50m ka hota hai. 5 jumps me packet train ke andar se escalator/exit gate tak aaraam se pahunch jata hai!

3.5. Single Hop me 50 Devices Broadcast (Omnidirectional Radio Waves)

  • Radio Broadcast: Bluetooth koi taar (wire) nahi hai. 10 meter ke daayre me khade **50 ke 50 phones ke Bluetooth chip ko packet sunai deta hai!**
  • RF Collision rokne ke 3 Rules:
    • 1. Random Jitter (20-80ms delay): Har phone thoda ruk kar aage fekta hai taaki radio signals aapas me na takrayein.
    • 2. Duplicate Suppression: Agar Phone 5 dekhta hai ki bagal wale Phone 2 ne wahi packet pehle bol diya, toh Phone 5 apna broadcast cancel kar deta hai.
    • 3. Low Battery Awareness: 20% se kam battery wale phones relay mode disable kar dete hain taaki unki battery bachi rahe.

4. Day 4 Mock Interview Repertoire (Ready English Scripts)

🎙️ QUESTION 1: Tamper Protection & Dual-Layer Validation
"What prevents an attacker sniffing intermediate Bluetooth hops from modifying the payment amount from ₹500 to ₹5,000?"
"Sir, ZeroMesh-UPI provides mathematically unbreakable dual-layer tamper protection:

First, at Stage 2 of the Ingestion Gateway, the server independently recalculates SHA-256(ciphertext) against the asserted packetId barcode in RAM. If an attacker modified any byte of the payload, the checksum mismatches and the packet is dropped within 2ms as TAMPERED without acquiring Redis locks or publishing to Kafka.

Second, even if an attacker recomputed both the ciphertext and packetId, the underlying transaction data is sealed using AES-256-GCM. GCM generates an authenticated 128-bit GMAC tag. During settlement decryption, any bit modification causes aes.doFinal() to immediately throw an AEADBadTagException, discarding the packet with zero database balance alterations."
🎙️ QUESTION 2: Replay Attack Defense & Two-Tier Deduplication
"What happens if an attacker captures a valid ₹500 payment packet and broadcasts it 50 times across different bridge nodes?"
"Sir, we implement a strict Two-Tier Deduplication Architecture:

At Tier 1 (Ingestion Gateway), the first arriving packet executes an atomic SETNX zeromesh:packet:<id> PROCESSING EX 90000 in Redis. When the 49 duplicate replay attempts hit our gateway instances, Redis returns false within sub-millisecond latency, rejecting all 49 copies as DUPLICATE before they can touch Kafka.

At Tier 2 (Core Banking), the PostgreSQL transaction_ledger table enforces a database-level UNIQUE constraint on packet_id. Even in the theoretical case of a Kafka redelivery, the relational database blocks duplicate ledger insertion, guaranteeing ₹0.00 duplicate money transfer."
🎙️ QUESTION 3: Mesh Broadcast Storm & Battery Exhaustion
"How does your peer-to-peer gossip protocol prevent broadcast storms and rapid battery drain across dense mobile crowds?"
"Sir, we mitigate mesh congestion through three cooperative mechanisms:

1. TTL=5 Hop Decay: Every intermediate peer decrements the packet's TTL counter. Upon reaching TTL=0, forwarding ceases immediately, strictly capping packet propagation to a 50-meter radius.

2. Random Jitter Delay (20-80ms): Peers introduce random transmission backoffs to prevent RF packet collision across simultaneous BLE broadcasts.

3. Duplicate Relay Suppression & Battery Gating: Nodes maintain in-memory LRU caches of seen `packetIds`. If an identical packet is overheard nearby, retransmission is suppressed, while devices below 20% battery automatically opt out of active relaying."
🎙️ QUESTION 4: Large-Scale DoS Flooding Defense
"What happens if a rogue actor floods your ingestion service with 1 million distinct synthetic packets?"
"Sir, our system defends in depth across four decoupled architectural boundaries:

Packets with forged hashes fail Stage-2 SHA-256 validation in sub-millisecond CPU memory without touching Redis or Kafka. Legitimate batch floods are throttled at the API Gateway via HTTP 429 rate limiting. Finally, any surviving malformed payloads that enter Kafka are dropped during settlement at the AES-GCM decryption step via `AEADBadTagException`, safely discarding the garbage without ever locking database rows or mutating account balances."
