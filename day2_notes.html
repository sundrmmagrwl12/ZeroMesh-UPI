1. Microservices Architecture & Complete Folder Structure

ZeroMesh-UPI ko ek single Monolith na bana kar humne Maven Multi-Module Microservices Architecture me divide kiya hai:

ZeroMesh-UPI (Parent Root POM) ├── 📦 common-mesh-dto ──> Shared Contract Library (Models, DTOs, Enums, Exceptions) ├── 🚀 ingestion-service ──> Port 8080 (Edge Gateway, Redis SETNX, Mesh Simulator, Cyber UI) └── 🏦 settlement-service ──> Port 8081 (Core Banking Engine, Kafka Consumer, Postgres ACID DB)

1.1. Proofs that ZeroMesh-UPI is a True Microservices Architecture

  • Independent Deployability: ingestion-service aur settlement-service dono ke paas apna alag pom.xml, apna alag Spring Boot main() class, aur alag Dockerfile hai. Dono ko independent containers me alag-alag scale kiya ja sakta hai.
  • Asynchronous Event-Driven Decoupling: Ingestion Service kabhi bhi Settlement Service ko direct synchronous HTTP REST se call nahi karti. Beech me Apache Kafka event backbone baitha hai.
  • Fault Isolation: Agar Bank ka PostgreSQL database ya Settlement Service down bhi ho jaye, tab bhi Ingestion Gateway 2ms me Dave ke offline packets accept karke Kafka me safely buffer karta rahega. Zero Data Loss!
  • Shared Canonical Data Model: common-mesh-dto shared library ki tarah kaam karta hai taaki dono services ek hi packet specification samajh sakein.

3. Apache Kafka KRaft Deep-Dive

3.1. Subway Rush Hour Problem (Kafka Kyu Lagaya?)

🚇 Rajiv Chowk 6:00 PM Scenario:
Metro subway train platform par aati hai. 500 passengers ke phones ek sath 5G network catch karte hain! 1 second ke andar 2,000 payment packets server par flood hote hain.

Agar Kafka NAHI hota (Direct Database Call):
PostgreSQL ka HikariCP connection pool (50-100 connections) 1 second me exhaust ho jata. Tomcat ke worker threads block ho jaate (Thread Starvation), aur server Dave ke phone ko HTTP 504 Gateway Timeout phenk deta. Payments drop ho jaati!

Kafka as Shock Absorber (Halwai & Cash Counter Analogy):
Ingestion Gateway (Cash Counter) 2 millisecond me packet Kafka topic me daal kar Dave ko HTTP 200 OK de deta hai. Settlement Engine (Halwai) parde ke peeche apni safe capacity (jaise 500 TPS) par aaram se DB likhta rehta hai. Zero connection exhaustion, zero dropped payments!

3.2. KRaft Mode (No ZooKeeper — Modern Kafka 3.x+)

Pehle Kafka chalane ke liye ek alag software (Apache ZooKeeper) lagta tha jo cluster metadata aur leader election manage karta tha. Isse 2 alag systems maintain karne padte the aur ZooKeeper failover slow hota tha.

Hamare docker-compose.yml me humne KAFKA_ENABLE_KRAFT: 'yes' configure kiya hai:

  • Single Binary: ZooKeeper container ko hamesha ke liye hata diya gaya hai.
  • Raft Consensus Protocol: Kafka brokers aapas me Raft algorithm se direct leader chun lete hain.
  • Sub-second Startup: Milliseconds me cluster ready ho jata hai aur partitions scale hote hain.

3.3. What is a Kafka Broker?

Kafka Broker = Ek individual server process (machine) jo messages receive karta hai, unhe disk par commit log me append karta hai, aur consumers ko serve karta hai.

  • Hamare Docker setup me port 9092 par chalne wala container hi Broker 1 (Node 1) hai.
  • Topic sirf ek logical naam hai. Messages asal me Broker ke hard drive par folder me save hote hain (e.g., /var/lib/kafka/data/mesh-payment-settlements-0/).
  • Production me hum 3 Brokers chalate hain taaki ek server crash hone par baaki do survive karein (High Availability).

3.4. Partitions, Hash Key, aur `%` Modulo Math (The Sequencing Bug)

Hamare topic mesh-payment-settlements me 3 Partitions hain. Jab Ingestion Service message publish karti hai, toh wo Sender UPI ID (jaise "sundram@upi") ko Message Key banakar bhejti hai:

kafkaTemplate.send("mesh-payment-settlements", packet.getPacketId(), payload);

🧮 Kafka ka Default Partitioner Formula:

Partition Number = Math.abs( MurmurHash2( key ) ) % Total Partitions

  • MurmurHash2("sundram@upi") = 1042783.
  • 1042783 % 3 = 1 ➔ Sundram ke saare packets HAMESHA Partition 1 par hi jayenge!
☠️ Out-of-Order Execution Disaster (Agar Hash Key Na Hoti):
Socho Sundram ke account me abhi sirf ₹1,000 hain.
• Txn 1 (12:00:00 PM): Salary Credit = +₹5,000 (Balance hona chahiye: ₹6,000).
• Txn 2 (12:00:01 PM): Phone Purchase = -₹4,000.

Agar dono packets alag-alag partitions par chale gaye (Txn 1 ➔ Part 0, Txn 2 ➔ Part 1):
Consumer 2 fast tha, usne Partition 1 se Txn 2 pehle utha liya! Usne dekha: Sundram ka balance sirf ₹1,000 hai aur khareedna ₹4,000 ka phone hai. Usne transaction `INSUFFICIENT_FUNDS` bolkar reject kar diya!
Uske baad Txn 1 credit hua. Sundram ka payment valid hote hue bhi fail ho gaya!

🏆 The Golden Rule: "Kafka guarantees message ordering ONLY within a single partition, never across multiple partitions!" Same partition me hone ki wajah se packets strictly FIFO (First-In, First-Out) order me settle hote hain.

3.5. Consumer Groups & Partition Assignment Rules

Hamari consumer service zeromesh-settlement-group me register hoti hai:

@KafkaListener(topics = "mesh-payment-settlements", groupId = "zeromesh-settlement-group")
Active Consumers Partition Allocation (3 Partitions) System Behavior
1 Consumer (Current Demo) Partitions 0, 1, 2 akela padhta hai Sequential processing across partitions. Memory-optimized for single container.
3 Consumers (Production Scale) Consumer 1 ➔ Part 0, Consumer 2 ➔ Part 1, Consumer 3 ➔ Part 2 Perfect 1:1 Parallelism! 3x Throughput without a single line of code change!

4. Offsets, Delivery Semantics & Two-Tier Idempotency

4.1. Kafka Offsets (Kitaab ka Bookmark 🔖)

Partition ke andar har message ka ek sequential number hota hai: Offset 0, 1, 2, 3.... Consumer jab message process kar leta hai, toh wo internal topic __consumer_offsets me apna bookmark commit karta hai.

4.2. Exactly-Once Processing Formula

Exactly-Once Processing = Kafka At-Least-Once Delivery + Two-Tier Idempotency

4.3. The Two-Tier Deduplication Truth (Redis vs DB Roles)

🚪 Do Darwaazon ka Architecture:
  • Tier 1: Ingestion Gateway (Port 8080 - Redis SETNX Gatekeeper):
    Dave jab packet flush karta hai, toh Redis par SETNX zeromesh:packet: PROCESSING EX 90000 lagta hai. Duplicate packets yahin 2ms me drop ho jaate hain aur Kafka me kabhi enter hi nahi hote!
  • Tier 2: Settlement Consumer (Port 8081 - PostgreSQL Database Unique Constraint):
    Kafka Consumer Redis me claim check NAHI karta! Agar Kafka ke at-least-once network retry se duplicate message consumer tak aa jaye, toh PostgreSQL transaction_ledger table ka packet_id UNIQUE constraint use pakadta hai. Settle hone ke baad consumer Redis me bas status idempotencyService.markSettled(packetId) update karta hai.

4.4. Producer ACKs (`acks = all`) & Idempotent Producer

Hamari application.yml me producer reliability configured hai:

spring:
  kafka:
    producer:
      acks: all   # Leader + Saare In-Sync Replicas (ISR) se receipt maangna compulsory!
  • Idempotent Producer (`enable.idempotence = true`): Producer har TCP batch ke sath ek Producer ID (PID) aur monotonically increasing Sequence Number bhejta hai.
  • ACK Drop Retry Scenario: Agar Broker ne message disk par likh liya lekin ACK raste me network drop ho gaya, Producer wahi sequence dobara bhejega. Broker dekhega ki ye sequence pehle se likha hai, toh disk par dobara nahi likhega, par Producer ko SUCCESS ACK bhej dega! Producer ko bina error ke receipt mil gayi aur disk par duplicate nahi bana!

4.5. Spring Boot Profile Inheritance (Why `acks: all` is in `application.yml`)

Spring Boot me application.yml base configuration hoti hai. application-docker.yml sirf child override hoti hai jisme sirf hostnames (jaise kafka:9092, postgres:5432) badalte hain. Saari core settings jaise acks: all, serializers, aur timeouts child profile me automatically inherit ho jaati hain (DRY Principle).

4.6. Consumer Lag & Dynamic Rebalancing

  • Consumer Lag: Produced Offset aur Consumed Offset ka gap. Agar lag badhta hai, toh consumer replicas badha kar throughput match kiya jata hai.
  • Rebalancing: Agar ek consumer node crash ho jaye (heartbeat timeout), toh Kafka Group Coordinator orphan partition ko surviving consumers me re-assign kar deta hai. System bina ruke chalta rehta hai.

5. Dead-Letter Topic (DLT) & Poison Pill Mitigation

Hamare code me @RetryableTopic laga hua hai:

@RetryableTopic(
    attempts = "3",
    backoff = @Backoff(delay = 1000, multiplier = 2),
    autoCreateTopics = "true",
    dltTopicSuffix = "-dlt"
)
@KafkaListener(topics = "mesh-payment-settlements", groupId = "zeromesh-settlement-group")
☠️ The Poison Pill & Head-of-Line Blocking Problem:
Agar kisi corrupted/malformed packet ki wajah se consumer par unhandled exception aayi, aur hum retry karte rahein, toh consumer infinite loop me phas jayega. Ek kharab packet ki wajah se uske peeche khade 10,000 genuine packets ruk jayenge (Head-of-Line Blocking)!

Hamara Solution: Consumer exponential backoff ke sath 3 attempts karta hai (1s ➔ 2s ➔ 4s). Agar teeno attempts fail ho jayein, toh message ko automatically `mesh-payment-settlements-dlt` (Dead-Letter Topic) me divert kar diya jata hai. Main partition free ho jata hai aur baaki saari payments aaram se process ho jaati hain!

6. Day 2 Mock Interview Repertoire (Ready English Scripts)

🎙️ QUESTION 1: Architectural Decoupling & Ingestion Bursts
"Why did you introduce Apache Kafka between Ingestion Gateway and Settlement Engine instead of a direct REST or database call?"
"Sir, we introduced Apache Kafka as an asynchronous shock absorber to prevent cascading thread starvation and database connection pool exhaustion during sudden traffic spikes.

In our subway mesh environment, hundreds of offline devices simultaneously catch cellular network at station exits, generating bursts of thousands of concurrent bridge flush requests. If handled synchronously against PostgreSQL, our HikariCP connection pool would choke within seconds, triggering HTTP 504 timeouts and dropped transactions.

Kafka decouples edge ingestion throughput (~2ms gateway response) from core banking settlement, allowing our consumer to drain transactions safely at a sustainable, rate-limited processing speed without upstream backpressure."
🎙️ QUESTION 2: Partitioning Strategy & Ordering Guarantees
"How did you design your Kafka partitioning strategy, and what happens if message keys are omitted?"
"Sir, Kafka guarantees strict FIFO ordering only within an individual partition, never across partitions. Our main topic is configured with 3 partitions, and we explicitly route messages using the sender's UPI ID as the Message Key.

Under the hood, Kafka's DefaultPartitioner applies Math.abs(MurmurHash2(key)) % 3, mathematically guaranteeing that all transactions originating from a specific user deterministically land on the exact same partition.

If keys were omitted, round-robin distribution would scatter a user's transactions across partitions. If a ₹5,000 salary credit landed on Partition 0 and a subsequent ₹4,000 purchase landed on Partition 1, a faster consumer thread on Partition 1 would evaluate the purchase first against the pre-salary balance, falsely declining the transaction with INSUFFICIENT_FUNDS due to out-of-order execution."
🎙️ QUESTION 3: Two-Tier Idempotency Architecture
"Does your Kafka Consumer query Redis or PostgreSQL for idempotency deduplication?"
"Sir, we operate a Two-Tier Deduplication Strategy with distinct separation of responsibilities:

1. At Tier 1 (Ingestion Gateway), we evaluate Redis SETNX with a 25-hour TTL. This serves as an ultra-fast, sub-millisecond edge filter that rejects duplicate mesh packets before they ever touch our Kafka cluster.

2. At Tier 2 (Settlement Consumer), the consumer does NOT execute a Redis claim. Instead, it relies on the PostgreSQL transaction_ledger table's unique constraint on packet_id to intercept rare Kafka at-least-once redeliveries. Once the atomic balance deduction and ledger record commit, the consumer simply marks the Redis status as SETTLED."
🎙️ QUESTION 4: Poison Pill Mitigation & Dead-Letter Topics
"How does your settlement consumer prevent Head-of-Line blocking when an unparseable or poisoned packet arrives?"
"Sir, unhandled exceptions on a poison message would cause consumer partitions to stall in an infinite retry loop, blocking thousands of healthy subsequent transactions behind it.

To eliminate Head-of-Line blocking, our consumer uses Spring Kafka's `@RetryableTopic` configured for 3 attempts with exponential backoff (1s, 2s, 4s). If all attempts are exhausted, the framework automatically routes the corrupted packet to our dedicated Dead-Letter Topic (`mesh-payment-settlements-dlt`). This unblocks the partition instantly, allowing healthy transactions to settle while isolating the poisoned payload for manual engineering audit."
